01

全体像 — EventKitとアプリの境界

RepositoryはEventKitの型をアプリ内部へ漏らさず、読み書きの窓口になります。

共有状態

shared を1つ使う

アプリ内の標準インスタンスは ReminderRepository.shared。ひとつの EKEventStore を所有します。

分離

actorでMainActorから分ける

EventKitアクセスと待機列をUIの実行領域から切り離します。プロトコルも Actor に準拠します。

境界

失敗を共通エラーへ

呼び出し側には ReminderRepositoryError を返し、EventKit固有の失敗を隠蔽します。

02

なぜactorだけでは足りないのか

actorは状態への同時アクセスを防ぎますが、非同期処理の完了まで排他的に占有し続ける仕組みではありません。

actorメソッドが await で停止すると、そのactorは別の呼び出しを実行できます。たとえば fetch() がEventKitのコールバックを待っている間に、別の create() が入り込むことがあります。どちらも同じ EKEventStore を触るため、このRepositoryでは「actorで状態を守る」ことに加えて「EventKit操作の実行権を1つにする」必要があります。

actorの保証

メモリ上の状態を安全に扱う

isOperating や待機配列を複数呼び出しが同時に書き換えるのを防ぎます。

追加の保証

EventKit操作を重ねない

取得・作成・更新・削除の各処理が完了するまで、次の操作に実行権を渡しません。

↳
ここが設計の要点
実行権は operation が取得し、defer に登録された releaseOperation() が成功・失敗どちらでも必ず返却します。

優先度付き直列化キュー

operation(priority:action:) がすべてのEventKit操作を包みます。

① 実行権を取得空いていれば即時開始
使用中なら待機列へ
›
② 権限を確認fullAccessでなければ
accessNotAuthorized
›
③ キャンセル確認Task.checkCancellation()
→ cancelled
›
④ action実行EventKitを読み書き
必要ならawait
›
⑤ 次へ引き継ぐ優先度順に起こす
なければ枠を解放
高 · 先に実行
現在このRepositoryから登録する操作はない
中 · FIFO
createupdatesetdelete
低 · FIFO

!
優先度は割り込みではありません。
実行中の処理は中断されません。待機列から次に誰を選ぶかだけを決めます。同じ優先度内では配列の先頭から取り出すため、登録順です。
// actionの途中でawaitしても、deferまで実行権を保持する await acquireOperation(priority: priority) defer { releaseOperation() } try checkAuthorization() try checkCancel() return try await action()
⚠
ネスト呼び出し禁止
operation のaction内から、同じく operation を使うRepositoryメソッドを呼ぶと、内側が外側の解放を待ち、外側が内側の完了を待つデッドロックになります。
04

各操作の中身

書き込み系は中優先度、一覧取得は低優先度で同じ実行枠を通ります。

メソッド主な流れ見どころ
createリストIDを解決 → 期限文字列を変換 → EKReminderを構築 → 保存グレゴリオ暦の年・月・日・時・分へ変換。期限と同時刻の相対アラームを追加します。
update対象取得 → 変更値の検証・変換 → 指定フィールドだけ更新 → 保存未指定の値は保持。期限変更では絶対日時アラームも期限の差分だけ移動します。
set対象取得 → isCompleted を設定 → 保存完了状態の切り替えを独立した操作として扱います。
delete対象取得 → eventStore.remove(..., commit: true)削除失敗は deleteFailed にまとめます。
fetch編集可能なリスト取得 → リマインダー取得 → リストごとに整形取得優先度は低。読み取りでも同じEventStoreを使うため、キューを通します。
期限変更

アラームを相対的にずらす

変更前後の期限から差分秒数を計算し、absoluteDate を持つ各アラームに加算します。相対オフセット型アラームはここでは変更しません。

日時変換

文字列をDateComponentsへ

JapaneseDateConverter の結果をグレゴリオ暦で分解し、EventKitへ渡します。変換できない値は deadlineConversionFailed。

05

fetch — 非同期コールバックをモデルへ

EventKitのcallback APIをasyncに橋渡しし、リスト単位の結果を組み立てます。

1
リストを絞るリマインダー種別のカレンダーから、編集可能なものだけ選ぶ。
2
取得を依頼predicateを作り、fetchRemindersのcallbackを待つ。
3
検証・分類EKReminderをReminderに変換し、listIDごとに辞書へ集約。
4
リストを返す各カレンダーに、対応する配列（なければ空配列）を詰める。
// callback API → async Result await withCheckedContinuation { continuation in eventStore.fetchReminders(matching: predicate) { reminders in // 有効なEKReminderだけをReminderへ変換 // [calendarIdentifier: [Reminder]] に分類 continuation.resume(returning: result) } }

callbackで nil が返れば fetchFailed。配列が返った場合も、モデル変換できなかった項目は辞書に追加されず、一覧から除外されます。

i
取得後にも確認
callback待ちのあいだに状態が変わる可能性を考慮し、取得結果を受け取った後にも権限とTaskキャンセルを確認してから返却します。
06

細部で迷いやすい点

型や変換に込められた意味を知ると、実装の意図が見えやすくなります。

3つの状態

notes: String??

外側のOptionalが「更新するか」を、内側が「値があるか」を表します。空文字とnilの扱いを明示できます。

nil変更しない
.some(nil)メモを消す
.some(.some("文"))その文字列を保存
境界で検証

EKReminder → Reminder

EKReminder+Reminder.swift の変換プロパティは、ID・タイトル・カレンダー、期限日、優先度、完了日時と作成・更新日時の整合性を確認します。条件を満たさなければ nil を返します。

優先度対応

EventKitとアプリの値を変換

EventKitの数値範囲をアプリの4段階にまとめます。0は未指定、1–4は高、5は中、6–9は低。保存時は各段階の代表値を使います。

キャンセル

待機中はすぐには抜けない

キューの待機continuationは非throwingです。待機中にキャンセルされても実行権を受け取るまでは待ち、その後 checkCancel() が検知します。EventKit callback自体をキャンセルする処理はありません。

↗
変更通知は「再取得して」の合図
EKEventStoreChanged を受けると remindersMayHaveChanged をpostします。通知にデータは載らないため、最新一覧は呼び出し側が fetch() で読み直します。
07

エラーはどこで決まるか

利用側が扱いやすい意味単位に変換しています。

共通ガード
  • accessNotAuthorized
    フルアクセスなし、または保存時の権限エラー
  • cancelled
    Taskがキャンセル済み
入力・対象
  • listNotFound / reminderNotFound
  • invalidTitle
  • deadlineConversionFailed
EventKit処理
  • fetchFailed
    取得callbackがnil
  • saveFailed
    保存時のその他のエラー
  • deleteFailed
    削除に失敗

権限要求そのものはRepositoryの責務ではありません。権限がない場合の要求UIは ReminderAccessRequestView が担当します。

08

読むときの短いまとめ

複雑さの中心を4点に縮めると、コードを追いやすくなります。

1

EventKitの共有窓口

1つのEventStoreを保持し、CRUDの入口をまとめる。

2

独自キューで直列化

actor再入が起きてもEventKit操作は同時に走らせない。

3

境界で変換・検証

アプリ型とEventKit型、文字列と日付、エラーを相互変換する。

4

通知は変更可能性だけ

通知を受け取った呼び出し側がfetchして最新状態を得る。
